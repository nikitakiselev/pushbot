# pushbot — источники переменных окружения и окружения GitHub

Дата: 2026-10-15
Статус: черновик, на ревью
Основная спека: `2026-10-14-pushbot-design.md`

## 1. Зачем

Сейчас у pushbot один источник переменных: вход `env` с строками `KEY=VALUE`,
значения берутся буквально. При переводе blog-v2 это дало три проблемы:

- В одно поле попадает два вида содержимого: сырые значения из секретов
  (их нужно брать буквально) и текст, скопированный из `.env` (его нужно читать
  как dotenv). pushbot их не различает, поэтому `APP_NAME="mBlog"` превращается
  в имя с кавычками, а `MAIL_FROM_NAME="${APP_NAME}"` записывается буквально.
  Ошибки нет, всё всплывает на проде.
- Весь `.env` лежит одним секретом. Секрет GitHub нельзя прочитать, поэтому
  чтобы поменять одну переменную, нужен весь файл целиком.
- Блок `env` в workflow свой у каждого проекта, а staging и production
  не описать одним манифестом.

Цель: всё, что нужно проекту, лежит в репозитории; значения секретов —
в GitHub Secrets; workflow одинаковый для всех проектов.

### Не входит

Хук `on_failure`, автооткат, переопределение пути проекта, управление
reverse proxy, ограничение деплоя по окружению в `allow`.

## 2. Три источника переменных

| Источник | Где задаётся | Что туда класть | Как pushbot его читает |
|---|---|---|---|
| Файл из репозитория | `env.file` в `pushbot.yml` | несекретные настройки | как есть, без разбора значений: кавычки и `${…}` обрабатывают compose и приложение |
| Секреты GitHub | имена — `env.secrets` в `pushbot.yml`, значения — GitHub Secrets | пароли, ключи, токены | буквально |
| Вход `env` action | `env:` у шага в workflow | вычисляемое в CI (`IMAGE_TAG`) и разовое | буквально, как сейчас |

Любой источник можно не использовать. Один ключ — ровно один источник:
ключ, пришедший из двух источников, — ошибка до деплоя.

Пример:

```yaml
# pushbot.yml
name: blog

files:
  - deploy/compose.yml: compose.yml

env:
  file: deploy/production.env
  secrets: [APP_KEY, DB_PASSWORD, REDIS_PASSWORD]

steps:
  - run: docker compose pull
  - run: docker compose up -d --remove-orphans
```

```yaml
# .github/workflows/deploy.yml — одинаковый во всех проектах
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
      packages: read
      id-token: write
    steps:
      - uses: actions/checkout@v4
      - uses: nikitakiselev/pushbot@v1
        with:
          url: https://pushbot.example.com
          secrets: ${{ toJSON(secrets) }}
          env: |
            IMAGE_TAG=${{ inputs.image_tag }}
```

## 3. Формат `pushbot.yml`: новые ключи

### `env`

```yaml
env:
  file: deploy/production.env   # необязательно
  secrets: [APP_KEY, DB_PASSWORD]  # необязательно
```

- **`file`** — путь к файлу в репозитории, правила как у `src` в `files`:
  относительный, без `..`, не директория. Файл не копируется в директорию
  проекта как отдельный файл, его содержимое становится частью `.env`
  (раздел 6). Если тот же путь указан и в `files`, он ещё и копируется — это
  разрешено.
- **`secrets`** — список имён. Имя — `^[A-Za-z_][A-Za-z0-9_]*$`, не
  начинается с `GITHUB_` (без учёта регистра: таких секретов GitHub не
  создаёт, а `github_token` в `.env` попадать не должен). Повтор имени, в том
  числе с другим регистром, — ошибка. Секрет ищется в GitHub без учёта
  регистра, как это делает сам GitHub; в `.env` ключ пишется так, как указан
  в манифесте.
- Неизвестные ключи внутри `env` — ошибка. `env: {}` допустим и ничего не
  задаёт.

### `environments`

```yaml
environments:
  production: {}
  staging:
    name: blog-staging
    files:
      - deploy/compose.yml: compose.yml
      - deploy/Caddyfile.staging: Caddyfile
    env:
      file: deploy/staging.env
```

- Ключ — имя окружения GitHub (`environment:` у job). Имена сравниваются без
  учёта регистра, как в GitHub; два ключа, отличающихся только регистром, —
  ошибка.
- Значение — переопределения. Можно задать только `name`, `files` и `env`
  с подключами `file` и `secrets`. Любой другой ключ, в том числе `steps`, —
  ошибка с пояснением: шаги общие для всех окружений, чтобы staging проверял
  ту же процедуру деплоя, что и прод; различия в шагах — через
  `$PUSHBOT_ENVIRONMENT`.
- Пустое значение (`production: {}` или `production:`) — окружение без
  переопределений.
- Каждый заданный ключ целиком заменяет значение верхнего уровня: `name` —
  `name`, `files` — весь список `files`, `env.file` — `env.file`,
  `env.secrets` — весь список `env.secrets`. Слияния списков нет.
  Переопределение задаёт значение, но не убирает его: если в одном
  окружении файл нужен, а в другом нет, `env.file` указывается в окружениях,
  а не на верхнем уровне.
- После переопределения итоговый манифест проходит те же проверки, что и
  манифест без окружений.

## 4. Выбор окружения

Окружение берётся из claim'а `environment` OIDC-токена. GitHub кладёт его
в токен, только если у job задан `environment:`.

| `environments` в манифесте | Окружение job | Результат |
|---|---|---|
| нет | любое или нет | верхний уровень, как сейчас |
| есть | есть в списке | верхний уровень + переопределения окружения |
| есть | не в списке | 400: `environment "stagng" is not listed in environments of pushbot.yml (production, staging)` |
| есть | у job нет `environment:` | 400: `pushbot.yml lists environments, but the job has no environment: set environment: in the workflow` |

Значения секретов для разных окружений задаются в GitHub Environments под
одинаковыми именами, поэтому список `env.secrets` обычно общий и задаётся на
верхнем уровне.

Если окружения на одном сервере, им нужны разные `name`: иначе они деплоятся
в одну директорию. pushbot это не проверяет — оба имени принадлежат одному
репозиторию.

## 5. GitHub Action

### Новый вход

| Вход | Обязателен | По умолчанию | Смысл |
|---|---|---|---|
| `secrets` | нет | пусто | `${{ toJSON(secrets) }}`: все секреты job'а в JSON |

### Поведение (изменения к разделу 5 основной спеки)

1. Получить OIDC-токен раньше, чем сейчас: до упаковки файлов.
2. Прочитать `environment` из payload токена (JWT, base64url). Подпись
   action не проверяет: значение нужно только чтобы выбрать файлы и секреты,
   решает всё равно сервер.
3. Через `yq` и `jq` вычислить для этого окружения `files`, `env.file`,
   `env.secrets` по правилам раздела 3. Проверку окружения (таблица
   раздела 4) action повторяет за сервером с тем же текстом ошибки: job
   с опечаткой в окружении не получает его секретов и иначе упал бы на
   «secret … is not set», указав не на ту причину. Кроме этого action
   проверяет только то, что читает сам: типы `files`, `env`, `env.file`,
   `env.secrets`, `environments` и имена секретов (то же правило, что
   у сервера). Остальное проверяет сервер.
4. Упаковать в `bundle.tgz` источники `files` и `env.file`. Отсутствующий
   `env.file` — ошибка до запроса. `env.file`, который уже попал в архив
   через `files` (сам или внутри каталога), второй раз не добавляется.
5. Если `env.secrets` не пуст:
   - вход `secrets` пуст — ошибка `env.secrets is set in pushbot.yml: add
     secrets: ${{ toJSON(secrets) }} to the pushbot step`;
   - для каждого имени найти секрет без учёта регистра; не найден — ошибка
     `secret DB_PASSWORD is not set in GitHub (environment staging): gh secret
     set DB_PASSWORD --env staging` (без окружения — без `--env`);
   - отправить поле `secrets`: JSON-объект только с объявленными секретами,
     ключи — как в манифесте.
6. Если `env.secrets` пуст, поле `secrets` не отправляется, даже если вход
   задан.
7. В лог: `pushbot: environment staging`, `pushbot: secrets APP_KEY,
   DB_PASSWORD` (только имена).

Action получает все секреты job'а, но отправляет только перечисленные
в манифесте. Это стоит указать в README: граница доверия — код action.

## 6. Демон

### API: новое поле `POST /v1/deploy`

- `secrets` — необязательно, JSON-объект `{"KEY": "value"}`, до 64 КБ.
  Битый JSON или не-строковое значение — 400.
- Набор ключей должен совпадать с `env.secrets` итогового манифеста:
  объявлен, но не прислан — 400 `secret DB_PASSWORD is declared in
  pushbot.yml but was not sent`; прислан, но не объявлен — 400 `secret X was
  sent but is not declared in env.secrets`.

### Конвейер (изменения к разделу 7 основной спеки)

На этапе подготовки, до ответа `200`, после распаковки архива:

1. Выбрать окружение и применить переопределения (раздел 4).
2. Прочитать `env.file` из распакованного архива: обычный файл, до 64 КБ,
   иначе 400. Извлечь из него ключи (ниже).
3. Проверить конфликты ключей между тремя источниками. Ключ в двух
   источниках — 400 `DB_PASSWORD is set both in secrets and in
   deploy/production.env; keep one`.
4. Проверить сырые значения (вход `env` и секреты):
   - значение целиком в двойных кавычках (`"…"`, длина ≥ 2) — 400 `APP_NAME:
     the value is wrapped in double quotes; env and secrets values are taken
     as is, remove the quotes`;
   - значение содержит `${KEY}`, где `KEY` — ключ из любого источника, —
     400 `MAIL_FROM_NAME: ${APP_NAME} is not expanded in env and secrets;
     move MAIL_FROM_NAME to the env file`;
   - значение содержит `'` или перевод строки — 400, как сейчас. В секрете
     перевод строки может прийти через JSON — тоже 400. То же для байта NUL:
     его не запишешь ни в `.env`, ни в окружение процесса.

Во время деплоя, в лог:

- для каждого сырого значения с `$$`: `==> warning: DB_PASSWORD contains
  "$$": env and secrets values are taken as is, so it stays "$$"`.

В тексте ошибок и предупреждений — только ключи, никогда значения.

### Ключи файла

pushbot не разбирает значения, но ключи ему нужны для проверки конфликтов.
Поддерживается такое подмножество dotenv:

- пустые строки и строки, первый непробельный символ которых `#`, —
  пропускаются;
- остальные строки — `[export ]KEY=…`, `KEY` по тому же правилу, что ключи
  входа `env`, пробелы вокруг `=` допустимы;
- если значение начинается с `"` или `'` и закрывающей кавычки на этой
  строке нет, значение продолжается на следующих строках до неё (кавычка
  после `\` не закрывает — в обоих видах кавычек, как читает docker
  compose). Незакрытая кавычка в конце файла — 400;
- BOM в начале файла отбрасывается: в середине `.env` он стал бы частью
  первого ключа;
- любая другая строка — 400 `deploy/production.env line 12: expected
  KEY=VALUE`;
- повтор ключа внутри файла — 400. Laravel берёт первое значение, compose —
  последнее, повтор почти наверняка ошибка.

### `.env`

Перезаписывается целиком, права `0600`, как сейчас. Части идут в порядке,
каждой непустой предшествует строка-комментарий:

```
# pushbot: env input
IMAGE_TAG='sha-abc1234'
# pushbot: secrets
APP_KEY='base64:…'
DB_PASSWORD='…'
# pushbot: deploy/production.env
APP_NAME="mBlog"
MAIL_FROM_NAME="${APP_NAME}"
```

- Вход `env` и секреты — `KEY='value'`, как сейчас.
- Файл — байт в байт; если он не кончается переводом строки, pushbot его
  дописывает.
- Сырые значения стоят раньше файла, поэтому файл может на них ссылаться
  (`DATABASE_URL="mysql://app:${DB_PASSWORD}@db/app"`): Laravel и compose
  подставляют только переменные, объявленные выше.

### Окружение шагов (изменения к разделу 7 основной спеки)

- Переменные из входа `env` и из секретов передаются в окружение шагов,
  как сейчас вход `env`.
- Переменные из файла в окружение шагов не передаются: pushbot не разбирает
  их значения. compose читает их из `.env` сам; в shell-шаге — `set -a;
  . ./.env; set +a`, если файл совместим с `sh`.
- Новая `PUSHBOT_ENVIRONMENT` — имя окружения из токена, пусто без него.

### Лог деплоя

```
==> nikitakiselev/blog@a1b2c3d (run #9876543210, environment staging) → /srv/apps/blog-staging
==> files: deploy/compose.yml → compose.yml (1 files)
==> .env: env IMAGE_TAG; secrets APP_KEY, DB_PASSWORD; deploy/staging.env (48 keys)
```

Без окружения — без `, environment …`. Без файла и секретов строка `.env`
такая же, как сейчас.

### Маскировка

Значения входа `env` и секретов маскируются в логах на сервере, как сейчас.
Значения из файла не маскируются: это несекретные настройки. README
предупреждает не класть секреты в файл.

## 7. Совместимость

- Манифест без `env` и `environments`: всё как раньше, кроме двух вещей —
  в `.env` перед значениями входа `env` появляется строка
  `# pushbot: env input`, и новые проверки
  сырых значений могут отклонить то, что раньше молча деплоилось
  с ошибкой. Это намеренно.
- Новый манифест на старом демоне: 400 с ошибкой строгого разбора YAML
  (`field env not found in type …`). Нужно обновить демон (`sudo pushbot upgrade`).
  С `env.secrets` старый демон отвечает раньше, на поле запроса: `unknown
  field "secrets"`. Action узнаёт этот ответ и пишет `the server is too old
  for env.secrets: run sudo pushbot upgrade on it`.
- Новый action (тег `v1` сдвигается) со старым демоном и старым
  манифестом: поле `secrets` не отправляется, архив тот же — работает.
- Релиз — `v1.4.0`.

## 8. Тестирование

- **manifest**: `env` (пути, имена секретов, `GITHUB_`, повторы с разным
  регистром, неизвестные ключи), `environments` (запрещённые ключи,
  пустые значения, имена с разным регистром), переопределения.
- **выбор окружения**: все четыре строки таблицы раздела 4, регистр.
- **auth**: claim `environment` разбирается, без него — пусто.
- **envfile**: ключи файла (`export`, кавычки, многострочные значения,
  экранированная кавычка, незакрытая кавычка, комментарии, мусорные строки,
  повторы); проверки сырых значений (`"…"`, `${KEY}` из каждого источника,
  `$$` → предупреждение, а не ошибка); раскладка `.env`.
- **server**: поле `secrets` (битый JSON, не-строка, лишний и недостающий
  ключ).
- **deploy**: `.env` из трёх источников, конфликт → 400,
  `PUSHBOT_ENVIRONMENT`, строки лога.
- **action** (`internal/e2e`, фейковый issuer): токен с `environment`,
  выбор файлов и секретов по окружению, ошибки «нет входа `secrets`»
  и «нет секрета».
- **E2E в CI**: тестовый манифест с `env.file` и `env.secrets`; вход
  `secrets` — JSON-строка прямо в workflow, настоящие секреты репозитория
  не нужны. Окружения в CI не проверяются: GitHub создал бы в репозитории
  окружение — хватает теста с фейковым токеном.

## 10. Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Хранилище секретов | GitHub Secrets | вводить секреты где-то всё равно нужно; GitHub уже есть, отдельный сервис не нужен |
| Несекретные настройки | файл в репозитории, кладётся в `.env` как есть | история и ревью через PR; dotenv-синтаксис работает так же, как локально |
| Где список секретов | `env.secrets` в манифесте, значения — `toJSON(secrets)` | всё о проекте в репозитории; workflow одинаковый для всех |
| Полный dotenv для входа `env` и секретов | нет, значения буквальные | иначе ломается `${{ secrets.X }}` с `$` в пароле |
| Ключ в двух источниках | ошибка | у переменной один источник, не нужно помнить приоритеты |
| Порядок в `.env` | сырые значения, потом файл | файл может ссылаться на секреты |
| Окружения | блок `environments`, окружение из OIDC-токена | шаги общие по построению; вход в action не нужен |
| Окружение не в списке | ошибка | опечатка не раскатит прод-конфиг |
| `steps` в окружении | нельзя переопределить | staging проверяет ту же процедуру, что и прод |
| `$$` в сыром значении | предупреждение | в случайном пароле `$$` законен |
