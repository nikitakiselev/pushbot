# pushbot — установка в две команды: install.sh и pushbot init

Дата: 2026-10-16
Статус: согласован
Основная спека: `2026-10-14-pushbot-design.md`

## 1. Зачем

Сейчас `install.sh` и ставит pushbot, и пишет конфиг:

```sh
curl -fsSL .../install.sh | sudo PUSHBOT_ALLOW='alice/*' sh
```

- Переменную приходится передавать внутрь `sudo`, а в ней помещается только один шаблон.
- Без переменной скрипт пишет заглушку и не запускает сервис, а дальше
  пользователь правит YAML руками.
- Опечатку в логине из `allow` видно только тогда, когда сервис падает при старте.
- Задать вопросы из `curl | sh` неудобно: stdin занят самим скриптом.

Цель: `install.sh` только ставит софт, а конфиг создаёт `pushbot init`. Это
либо пошаговый мастер, либо одна команда с флагами для скриптов и агентов.

```sh
curl -fsSL https://raw.githubusercontent.com/nikitakiselev/pushbot/main/install.sh | sudo sh
sudo pushbot init
```

### Не входит

Настройка reverse proxy, вопрос о публичном адресе, флаги для редких
настроек (`deploy_timeout`, лимиты, `state_dir`, `audience`), сохранение
комментариев пользователя в существующем конфиге.

## 2. pushbot init

Только Linux и только от root, как `doctor` и `upgrade`.

### Режимы

| Условие | Режим |
|---|---|
| передан любой флаг настройки (`--allow`, `--listen`, `--projects-root`, `--metrics-listen`) | без мастера: собрать, проверить, записать, запустить; вопросов нет |
| флагов настроек нет, stdin и stdout — терминал | мастер (charmbracelet/huh) |
| флагов настроек нет, терминала нет | ошибка `no terminal for the wizard: pass the settings as flags` |

Если без мастера в итоге не получилось ни одного шаблона `allow` (свежий
сервер и нет `--allow`), это ошибка с подсказкой `pass --allow`.

### Флаги

| Флаг | Ключ | По умолчанию |
|---|---|---|
| `--allow` (повторяемый) | `allow` | — |
| `--listen` | `listen` | `127.0.0.1:9800` |
| `--projects-root` | `projects_root` | `/srv/apps` |
| `--metrics-listen` | `metrics_listen` | пусто (метрики выключены) |
| `--force` | — | перезаписать существующий конфиг в режиме без мастера |
| `-c`, `--config` | — | `/etc/pushbot/config.yml` |

### Откуда берутся значения

Основа — существующий конфиг, если он есть и читается, иначе значения по
умолчанию. В режиме без мастера флаги перекрывают основу (`--allow` заменяет
список целиком); мастер показывает основу. Ключи, о которых мастер не спрашивает,
переносятся из существующего файла как есть. Если существующий файл не
читается, выводится предупреждение и основой становятся значения по умолчанию.

### Мастер

Одна форма huh из двух групп. Несколько форм подряд в одном процессе теряют
нажатия: первый Enter во второй форме после подтверждения пропадал.

1. Первая группа:
   - `allow`: одна строка, шаблоны через запятую или пробел. Каждый шаблон
     проверяется (`owner/repo-pattern`), каждый владелец ищется на GitHub.
     Если владельца нет, это ошибка в поле. Если GitHub недоступен, поле
     проверку проходит, а предупреждение печатается при записи.
   - `listen`: `host:port`.
   - `projects_root`: абсолютный путь.
   - `metrics_listen`: `host:port` или пусто, тогда метрики выключены.
2. Вторая группа: путь и итоговый файл без комментариев и пустых строк (полный
   файл занимает около 20 строк и не помещается: huh ограничивает высоту
   группы), затем вопрос «Correct?». «Yes» — записать и запустить. «No» и
   Ctrl+C — выйти, ничего не записав. Shift+tab — вернуться к настройкам, значения
   сохраняются.

### Существующий конфиг

- Мастер показывает его значения и перезаписывает файл после «Yes».
- Режим без мастера без `--force` отказывается:
  `/etc/pushbot/config.yml exists: run pushbot init without flags to edit it, or pass --force`.
- Перед перезаписью старый файл копируется в `config.yml.bak`.

### Что делает запись

1. Итоговый YAML проходит через `config.Parse`. Ошибка — выход, ничего не записано.
2. Владельцы из `allow` ищутся на GitHub (с `GITHUB_TOKEN`, если задан).
   Если владельца нет, это ошибка. Если GitHub недоступен, это предупреждение.
   В мастере результаты уже есть, повторно запросы не идут.
3. Файл записывается атомарно с правами 0644. Папка конфига создаётся с правами 0755.
4. Если `projects_root` нет, папка создаётся с правами 0750 и владельцем
   `pushbot:pushbot`. Если пользователя `pushbot` нет, выводится предупреждение.
5. Сервисом команда управляет, только когда установлен
   `/etc/systemd/system/pushbot.service` и конфиг лежит по стандартному пути
   (юнит читает именно его):
   - `systemctl enable --quiet pushbot` и `systemctl restart pushbot` (перезапуск
     дожидается деплоев, которые уже идут);
   - ожидание `/healthz` на адресе `listen` до 75 секунд: при старте pushbot
     до минуты пытается найти владельцев. Если сервис перестал быть active,
     ожидание прерывается сразу. Ошибка — выход с кодом 1 и подсказкой
     `sudo journalctl -u pushbot -n 50`.

   В остальных случаях печатается `pushbot serve --config <path>`.
6. Печатается следующий шаг: пример Caddy с реальным `listen`, ссылка на
   раздел про reverse proxy и `sudo pushbot doctor --url https://...`.

### Формат файла

Шаблон с комментариями. Заданные ключи пишутся явно, незаданные редкие
настройки остаются закомментированными со значениями по умолчанию.
Значения экранируются как скаляры YAML.

```yaml
# pushbot configuration, written by pushbot init.
# After changes: sudo systemctl restart pushbot
# Docs: https://github.com/nikitakiselev/pushbot#daemon-config
listen: 127.0.0.1:9800
projects_root: /srv/apps
# Repositories that may deploy, owner/repo-pattern: the owner is literal,
# the repository name is a pattern.
allow:
  - alice/*
# Prometheus metrics at /metrics on a separate address (disabled when empty):
# metrics_listen: 127.0.0.1:9801

# Optional settings, defaults shown:
# state_dir: /var/lib/pushbot
# audience: pushbot
# deploy_timeout: 15m
# max_bundle_size: 50MB
# max_unpacked_size: 200MB
# log_retention: 20
```

`oidc_issuer` (для тестов) пишется только тогда, когда он задан.

## 3. install.sh

Остаётся как есть: проверки, загрузка, бинарник, юнит, пользователь `pushbot`
в группе `docker`, `/var/lib/pushbot`, `/etc/pushbot`.

Из скрипта убирается запись конфига, создание `/srv/apps` и печать примера Caddy.

Скрипт заканчивается одним из трёх случаев:

- конфиг есть (повторный запуск, обновление): `daemon-reload`, `enable`, `restart`;
- конфига нет, задан `PUSHBOT_ALLOW`: `pushbot init --allow "$PUSHBOT_ALLOW"`.
  Это совместимость со старой командой, в документации переменной больше нет;
- конфига нет: `daemon-reload` и подсказка `sudo pushbot init`. Без `enable`:
  иначе после перезагрузки сервис без конфига падал бы каждые 5 секунд.
  `enable` выполняет `init`.

Бинарник ставится из релиза, а `install.sh` всегда берётся из `main`. Поэтому
релиз может оказаться без `init`: `PUSHBOT_VERSION` указывает на старый релиз,
или `main` уже слит, а релиз ещё не выпущен. Если при этом конфига нет, скрипт
останавливается с ошибкой `pushbot X is too old to create its config`. Отсюда
порядок выпуска: релиз сразу после слияния в `main`.

## 4. Код

- `internal/config`:
  - экспортированные значения по умолчанию;
  - тип `File` (бывший `rawConfig`): конфиг в том виде, как он записан;
  - `ReadFile`;
  - `File.Render`;
  - `ValidateAllow` и `ValidateAddress` для проверки отдельных полей;
  - `DialAddr` (бывший `doctor.localAddr`);
  - `Parse` начинает проверять `listen` как `host:port`, как уже проверяет
    `metrics_listen`. Такой `listen` раньше всё равно не проходил `net.Listen`.
- `internal/setup`:
  - `Owners` — поиск владельцев с кэшем;
  - `Run(ctx, Options)` — шаги из раздела «Что делает запись».

  Всё внешнее приходит через `Options`: systemctl, HTTP-клиент, chown, вывод.
- `cmd/pushbot/init.go`: cobra-команда, флаги, выбор режима (`useWizard`),
  форма huh, предпросмотр (`preview`).
- Зависимость `charm.land/huh/v2`. Проверено, что она собирается вместе с fang v1.0.0
  (lipgloss поднимается до стабильной v2).

## 5. Тесты

- `config`:
  - круговая проверка `Render` → `Parse` и `Render` → `ReadFile`;
  - ключи, о которых мастер не спрашивает, сохраняются;
  - значения, которым нужны кавычки, экранируются;
  - неверный `listen`.
- `setup.Run` во временной папке с подставным systemctl, GitHub и `/healthz`
  подменены через `httptest`. Случаи:
  - новый файл;
  - существующий файл без перезаписи;
  - перезапись с `.bak`;
  - владелец не найден;
  - GitHub недоступен (предупреждение, запись продолжается);
  - сервис не управляется (нестандартный путь);
  - `/healthz` не отвечает;
  - сервис упал во время ожидания;
  - создание `projects_root`.
- Выбор режима (`useWizard`), разбор строки `allow` и предпросмотр — обычные
  функции, проверяются таблицами.
- Вживую на Ubuntu 26.04 с systemd (OrbStack): установка без конфига, мастер
  (ошибка владельца в поле, возврат по shift+tab, «Yes», «No», Ctrl+C), повторный
  мастер на существующем конфиге, флаги с `--force` и без, `PUSHBOT_ALLOW`,
  повторный `install.sh`, старый релиз без `init`, падение сервиса на занятом порту.
- Сама форма huh юнит-тестами не покрывается.
